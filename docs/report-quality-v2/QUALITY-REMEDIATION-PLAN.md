# Cosmic Spirit Guide Report Quality Review and Remediation Plan

Author: John (content direction)
Date: 2026-08-25
Scope: all eight production n8n report samples in `report-review/results/`
Decision: **NO-GO for customer delivery or domain cutover. Keep report purchases disabled.**

## 1. Executive verdict

The writer model is not the primary problem. The strongest samples show that Kimi can produce a warm, specific Cosmic Spirit Guide voice. The dominant failure is that the production workflows do not receive or enforce the full deterministic fact set promised by the product briefs.

The correct remediation is:

1. Complete and normalize the verified-facts layer.
2. Validate each report's required inputs before calling the writer.
3. Wire each per-report brief into the runtime prompt and deterministic validator.
4. Replace loose citation, length, placeholder, and judge checks with exact per-section gates.
5. Regenerate the seven component reports.
6. Build Full Cosmic by assembling approved component reports, never as one standalone prompt.
7. Perform human editorial approval and final visual/PDF review.

The governing product principle is **narrative-first interpretation**: deterministic facts
are the evidence, but the customer-facing value is the cohesive story those facts create
about this person's unique gifts, tensions, developmental path, timing, choices, and useful
next steps. Reports must never collapse into cold data tables, disconnected placement
definitions, or generic advice. Narrative may interpret verified facts but may not invent
biography, trauma, relationships, occupations, or life events.

Do **not** hand-edit the current drafts into deliverables. They would remain unrepeatable one-offs generated by a broken contract.

## 2. What the statuses actually mean

- `approved`: automated free-tier gates passed. This does not prove the complete rendered product meets the product brief.
- `needs_editor`: the expected intermediate status for a paid report that passed automated gates. It is intentionally withheld until a human editor submits an approval decision.
- `rejected`: a hard gate or score failed. It must not be delivered.

Therefore, the desired paid-report flow is:

`generated -> automated gates pass -> needs_editor -> John/editor review -> approved`

We should not change paid workflows to auto-approve. We should make `needs_editor` trustworthy.

## 4. Shared root causes

### A. Incomplete verified-facts contract

The current natal payload provides planets, houses, ASC, and MC, mostly as absolute longitude. It does not provide the full report-ready derived layer.

Required normalized fields include:

- Both `longitude` and `degreeInSign` for every body, angle, and cusp.
- Display label preformatted by code, e.g. `Venus 18.68° Taurus, 9th house`.
- ASC, DSC, MC, IC and their rulers.
- Chart ruler and condition.
- South Node and Part of Fortune.
- Juno where required.
- Major/minor aspects with orb, exactness, and stable IDs.
- Top aspects by planet/body.
- Detected patterns with stable IDs, participants, and tightness.
- Element/modality tallies based on one locked inclusion rule.
- Computed Moon phase.
- Dignity as an explicit enum; null means no dignity language.
- Report-specific archetype codes and driver IDs.
- Report-specific deterministic score bands and drivers.
- Full transit event ledgers with exact dates, stations, ingresses, returns, eclipses, active/quiet months, and topic scores.

### B. Required facts are not validated before generation

Production currently checks only that `verifiedFacts` is a non-empty object. Each report needs a versioned JSON schema and report-specific preflight validator. A missing required field should create an internal `input_incomplete` result—not customer-facing placeholder prose.

### C. Written briefs are not fully wired into runtime

The workflow generator embeds global voice/quality text and prompt files but does not embed the per-report `.brief.md` containing the authoritative facts-to-cite table. The runtime therefore lacks the exact coverage contract it is supposed to enforce.

### D. Deterministic gates are too loose

Current problems:

- No hard rejection for unresolved `{{MISSING_FACT:...}}`.
- Citation checking only searches loose numbers somewhere in the full fact blob.
- It does not resolve a citation to an exact JSON path and value.
- No deterministic word bounds or page/module coverage.
- No required-field-used coverage check.
- No cross-report duplicate check.
- No validation of degree-within-sign versus longitude.
- Rejected draft sections are discarded.

Use structured fact references such as:

```json
{
  "factId": "natal.venus.position",
  "display": "Venus at 18.68° Taurus in the 9th house"
}
```

The renderer/linter—not the model—should resolve and verify the final display.

### E. Judge implementation does not match the documented quality bar

The judge currently receives gate names, facts, and report JSON, but not the full detailed rubric as an authoritative judging prompt. It emits one aggregate scorecard, while the locked quality bar requires a scorecard per section.

Required judge behavior:

- Per-section hard gates and seven scored dimensions.
- One evidence-backed justification per score.
- Coverage score against that section’s required facts.
- Deterministic hard-gate results cannot be overridden by the model judge.
- Aggregate verdict computed from section results, not guessed.
- No perfect score when a required fact, section, date, module, or placeholder is missing.

### F. Product scope and page-count math are inconsistent

At the current word bounds:

- Love Blueprint: roughly 1,070–1,540 words, or about 3.1–5.1 text pages at the stated 300–350 words/page.
- Vocation: roughly 930–1,340 words, or about 2.7–4.5 text pages.
- Karmic: roughly 850–1,240 words, or about 2.4–4.1 text pages.
- Yearly Transit: roughly 1,670–2,490 words, or about 4.8–8.3 text pages.

Do not pad. Either:

1. Lower the promised page ranges honestly, or
2. Add real premium modules—tables, evidence cards, calendars, diagrams, exercises, summaries, and chart visuals—and specify their page allocation.

Recommendation: keep the premium targets only where the additional modules are real and useful. Define a page map for every SKU before another launch review.

## 5. Required production pipeline

```text
birth/chart data
-> normalized computed fact ledger
-> report-specific schema preflight
-> deterministic tables/scores/timelines
-> writer with global brief + per-report brief + exact fact references
-> strict parser
-> placeholder/structure/coverage/length/factual/duplication lint
-> one bounded revision using the same complete brief
-> second deterministic lint
-> per-section independent judge
-> free: approved if all gates pass
-> paid: needs_editor if all gates pass
-> human editorial decision
-> approved
-> final app/PDF assembly and visual QA
-> delivery
```

## 7. Definition of done

A report is launch-ready only when:

- Its report-specific input schema passes.
- Every required deterministic fact/module exists.
- No model-derived celestial arithmetic or display conversion occurs.
- Every factual citation resolves to one exact fact ID/value.
- Every required section/module is present and correctly ordered.
- No placeholders, duplication, unsafe claims, or unsupported psychology.
- Its actual rendered length/value matches the SKU promise.
- Automated per-section judge passes honestly.
- Paid reports receive explicit human approval.
- Final app/PDF presentation is visually approved.

The current samples are useful diagnostic evidence, not launch inventory.

- Relationship, Love Timing, Yearly Transit, and Karmic must remain rejected.
- Love Blueprint and Vocation must remain in review and should be regenerated after the foundation fix rather than manually approved.

Customer purchases and domain cutover remain blocked.
